## Як читати цей файл

- Кожен тикет має унікальний код: `S<спринт>-<модуль>-<номер>`
  (наприклад `S2-INFRA-01`).
- **Залежності** — це коди тикетів, які мають бути завершені (включно з
  тестами) до початку цього тикета. Тикети без залежностей можна брати в
  роботу одразу після старту відповідного спринту.
- **Acceptance criteria** — вичерпний перелік умов, при виконанні яких тикет
  вважається закритим. Якщо хоч один пункт не виконано — тикет не готовий до
  Pull Request.
- **Тести** — обов'язкова частина acceptance criteria, не окремий необов'язковий
  додаток. Тикет без тестів, вказаних у ньому, не вважається завершеним
  незалежно від того, чи працює функціонал вручну. Усі тести з тикета мають
  проходити локально (`pytest` для backend, наявний test runner для frontend
  там, де тести вже ведуться) до відкриття Pull Request.
- **Чекліст** наприкінці кожного тикета — заповнюється виконавцем (`[x]`)
  перед тим, як відкривати Pull Request. Незакреслений пункт = тикет не
  готовий, незалежно від того, що написано в описі PR.
- Роботу над кожним тикетом починати з гілки `feature/<код-тикета>-<короткий-опис>`
  від актуального `develop`, відповідно до git-flow з `CLAUDE.md`.
- Усі backend-ендпоінти мають бути під префіксом **`/api/`**
  (наприклад, `/api/health`, `/api/projects`, `/api/projects/{id}/documents`).
  Немає жодного продакшн-ендпоінту без цього префікса.
- Backend та всі Python-сервіси — **Python 3.14**.

## Модуль: DOCKER & DEPLOYMENT

### S2-DOCKER-01 — Кореневий `docker-compose.yml` та скелет Dockerfile'ів по сервісах

**Опис:** Створити кореневий `docker-compose.yml`, що піднімає всі сервіси
проєкту одною командою, і базові `Dockerfile` в кожній відповідній теці.
Структура на верхньому рівні репозиторію:

```
/
├── docker-compose.yml        # єдина точка входу: піднімає всі сервіси разом
├── CLAUDE.md
├── TASKS.md
├── backend/
│   └── Dockerfile            # основний API (FastAPI)
├── frontend/
│   └── Dockerfile
├── mail/
│   └── Dockerfile            # образ самого поштового сервера (Postfix/Dovecot чи еквівалент)
└── workers/
    ├── mail-processing/
    │   └── Dockerfile        # окремий воркер: обробка вхідних листів
    ├── document-processing/
    │   └── Dockerfile        # окремий воркер: обробка документів/нормативів
    └── report-generation/
        └── Dockerfile        # окремий воркер: генерація/збірка звітів
```

Кожен воркер у `workers/` — окремий Dockerfile і окремий процес запуску
(`CLAUDE.md` §2.2: «1 сервіс — 1 задача»), навіть якщо на ранньому етапі вони
шарять один і той самий Python-код з `backend/app` (через спільний build-
контекст або встановлення backend-пакета всередину образу воркера — на розсуд
виконавця, задокументувати обране рішення в `README.md` кореня).

**Залежності:** немає.

**Acceptance criteria:**
- Кореневий `docker-compose.yml` описує всі сервіси: `backend`, `frontend`,
  `mail`, `worker-mail-processing`, `worker-document-processing`,
  `worker-report-generation`, `postgres`, `redis`.
- Кожен сервіс, що має власний код (backend, frontend, mail, кожен з трьох
  воркерів), має свій `Dockerfile` у відповідній теці — без спільного
  «монолітного» Dockerfile на кілька сервісів одразу.
- Усі Python-образи побудовані на базі **Python 3.14**.
- `docker compose up` з кореня репозиторію піднімає всі сервіси без ручних
  додаткових кроків, окрім заповнення `.env` (задокументовано в
  кореневому `README.md`).
- **Тести:** інфраструктурний тикет — замість `pytest` перевіркою є: після
  `docker compose up` сервіс `backend` проходить власний health-check
  (`GET /api/health`, див. S2-INFRA-01) із хоста.

**Чекліст перед PR:**
- [ ] Кореневий `docker-compose.yml` створено і описує всі сервіси зі списку вище
- [ ] `backend/Dockerfile` створено
- [ ] `frontend/Dockerfile` створено
- [ ] `mail/Dockerfile` створено
- [ ] `workers/mail-processing/Dockerfile` створено
- [ ] `workers/document-processing/Dockerfile` створено
- [ ] `workers/report-generation/Dockerfile` створено
- [ ] Усі Python-образи використовують Python 3.14
- [ ] `docker compose up` піднімає все без помилок на чистому середовищі
- [ ] `GET /api/health` доступний з хоста після підняття
- [ ] `.env.example` і кроки запуску задокументовані в кореневому `README.md`

## Підсумкова умова готовності MVP

MVP вважається завершеним, коли:
1. Усі тикети Спринту 2 і Спринту 3 закриті за їхніми acceptance criteria,
   і чекліст кожного тикета заповнений повністю.
2. Повний набір тестів (`pytest tests/`) проходить без помилок і без
   пропущених (skipped) тестів, окрім свідомо задокументованих винятків.
3. `black --check .` і `ruff check .` (backend), `eslint`/`prettier`
   (frontend) проходять без помилок.
4. `docker compose up` з кореня репозиторію піднімає всі сервіси
   (backend, frontend, mail, три воркери, postgres, redis) без ручних
   додаткових кроків, окрім `.env`.
5. Усі backend-ендпоінти доступні під префіксом `/api/`.
6. Наскрізний сценарій з S3-E2E-01 відтворюваний не лише в тесті, а й вручну
   через UI на пілотному матеріалі.
