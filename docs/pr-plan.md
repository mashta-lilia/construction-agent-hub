# Розбивка на PR

> **Статус: план нижче (PR 1-12) реалізовано одним PR #5 (S2-FE-01),
> замість пошагового порту.** Порт прототипу не ділився на самодостатні PR:
> кожен крок залишав частину компонентів у вигляді тимчасових заготовок, які
> довелося б віддавати на рев'ю ще раз, коли вони отримають справжню
> реалізацію. Тому зроблено одним внеском, з явним застереженням про розмір
> діффу в описі PR. Таблиця нижче лишається як історія рішення, не як
> актуальний план.
>
> Реальні залишки з рев'ю PR #5, кожен — окремий маленький PR від
> `develop`:
>
> - `frontend/src/services/apiClient.ts` відновлено — це спільна обв'язка
>   запитів: `apiRequest` з базовою адресою, таймаутом, серіалізацією JSON,
>   клас `ApiError` і безпечний розбір відповіді (зокрема порожнього тіла).
>   Доменних викликів у ньому немає й не буде — вони належать
>   `features/<name>/services` (CLAUDE.md §2.1). Конкретні ендпоінти та
>   генерація типів (`npm run api:types`) додаються в тому PR, що вперше
>   робить робочий backend-виклик, не раніше (див. `docs/api-contract.md`).
> - Доступність (aria) для Dialog/CommandPalette, `useFocusTrap` — виправлено
>   в тому ж PR, що й `nginx.conf`/`.dockerignore`-фікс.

## Гілки

За `CLAUDE.md` 4: гілка створюється від актуального `develop` з префіксом
`feature/` (або `fix/`, `chore/`), вливається в `develop` через PR з ревʼю,
у `main` йде тільки продакшн-готовий код. Прямий пуш у `main` заборонений.

Зверніть увагу: `RULES.md` 1 описує інший процес — GitHub Flow без `develop`.
Розбіжність між двома документами варто закрити до першого PR.
