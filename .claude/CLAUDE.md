# CLAUDE.md — RECONSTRUCTION HUB

Ці правила діють для всього монорепозиторію (frontend + backend). Мета —
щоб код, написаний у різних сесіях і різними людьми/агентами, виглядав так,
ніби його писала одна людина: однакова структура, однакові інструменти,
однаковий git-flow.

Якщо будь-яка інструкція користувача в чаті суперечить цьому файлу —
слідувати інструкції з чату для поточної задачі, але не переносити
відхилення в структуру проєкту без явного прохання.

---

## 1. Контекст проєкту (коротко)

Reconstruction Hub — веб-платформа для головного інженера будівельних
проєктів. Ключова автоматизація: коли підрядник пропонує замінити
будівельний матеріал листом на пошту проєкту, система порівнює
запропонований матеріал із проєктним за ціною/характеристиками/наявністю/
відповідністю нормам (ДСТУ/ДБН) і формує звіт із рекомендацією. Остаточне
рішення завжди ухвалює інженер — система ніколи не є джерелом істини,
лише рекомендацією.

MVP охоплює один тип користувача (головний інженер, повний доступ) і один
пілотний тип будівельного матеріалу. Загальний конвеєр обробки
(документ → розпізнавання → порівняння → висновок → звіт) має бути
написаний узагальнено, без хардкоду під конкретний матеріал — перелік
характеристик для порівняння визначається з нормативного документа, а не
зашивається в код.

### Рішення по відкритих питаннях ТЗ (зафіксовано, не перевідкривати без прямого запиту замовника)

| Питання ТЗ | Рішення |
|---|---|
| 7.1 Спосіб визначення розділу документа | Комбінований: інженер може обрати розділ вручну, і система пропонує автовизначення розділу — обидва шляхи мають бути в UI/API |
| 7.2 Поштовий сервіс | Окрема поштова адреса для кожного проєкту, власний поштовий сервер (self-hosted SMTP, напр. Postfix/аналог) у Docker, а не сторонній SaaS-провайдер |
| 7.3 Режим обробки нормативної бази | Напівавтоматичний: система готує чернетку розпізнаного змісту, інженер перевіряє й підтверджує — це має бути окремий explicit крок у workflow, не "тихе" автоматичне збереження |
| 7.4 Постачальник AI | Наразі OpenRouter, але шар доступу до AI-провайдера має бути повністю абстрагований (інтерфейс), заміна провайдера не повинна вимагати змін поза цим шаром |
| 7.5 Бюджет | Наразі не є обмеженням для архітектурних рішень |

Приховування чутливих даних перед відправкою на будь-який зовнішній
AI-сервіс — обов'язкова вимога, а не опція. Це реалізується як окремий,
тестований крок конвеєра, що виконується до будь-якого виклику
зовнішнього AI, ніколи не всередині одного "великого" методу разом з
іншою логікою.

Перелік того, що приховується, задається списком, а не «на око», і
покриває весь вміст листа підрядника, а не тільки проєктні поля:
- імена людей і назви організацій (підрядник, замовник, субпідрядники);
- контакти: email, телефони, месенджери, підписи в кінці листа;
- назви й адреси об'єктів, локації, географічні прив'язки;
- суми, ціни, номери договорів, рахунків, специфікацій;
- ідентифікатори проєкту/документа (розділ 11 — назовні йде тільки
  непрозорий ідентифікатор, не внутрішній `projectId`);
- вільний текст листа, з якого ці дані не вдалося структуровано
  вилучити.

**Санітайзер працює за принципом fail-closed:** якщо хоча б одне поле не
вдалося класифікувати або впевнено знеособити — **відхиляється весь
payload** із явною помилкою, і виклик зовнішнього AI не відбувається
взагалі. Не «викинемо проблемне поле й підемо далі» і не «відправимо як
є, бо ризик невеликий»: часткове очищення дає хибне відчуття безпеки,
бо неможливо довести, що видалене поле не залишило слідів у сусідніх.
Такий запит повертається інженеру як «потребує ручної перевірки», а
звіт, що спирався б на ці дані, не формується. Мовчазний пропуск
невідомого поля назовні — дефект, а не крайній випадок.

## 2. Структура репозиторію

Монорепо, два корені: `frontend/` і `backend/`.

### 2.1 Frontend — обов'язкова структура (feature-based)

```text
frontend/
├── Dockerfile
├── README.md
├── index.html
├── package.json
├── package-lock.json
├── public/
│   └── favicon.png
├── src/
│   ├── main.tsx
│   ├── App.tsx
│   ├── App.css
│   ├── index.css
│   ├── assets/
│   ├── components/          # спільні (dumb) UI-компоненти без бізнес-логіки
│   │   └── ComponentName/
│   │       ├── ComponentName.tsx
│   │       └── ComponentName.css
│   ├── features/
│   │   ├── auth/
│   │   │   ├── components/  # компоненти, специфічні для фічі
│   │   │   ├── hooks/
│   │   │   ├── services/    # API-виклики та бізнес-логіка фічі
│   │   │   ├── types/
│   │   │   ├── auth.css     # ОДИН css-файл на весь feature (+ Bootstrap-класи)
│   │   │   └── index.ts     # публічний barrel-експорт фічі
│   │   ├── projects/
│   │   ├── documents/
│   │   ├── reports/
│   │   ├── norms/
│   │   └── inbox/
│   ├── hooks/                # спільні хуки (не прив'язані до конкретної фічі)
│   ├── lib/
│   ├── pages/                # route entry points: композиція фіч, без власної бізнес-логіки
│   ├── providers/            # theme, i18n, auth-context тощо
│   ├── routes/                # конфігурація React Router
│   ├── services/              # глобальний API-клієнт (axios/fetch instance, interceptors)
│   ├── store/                  # Zustand stores (глобальний UI/сесійний стан)
│   ├── types/                  # спільні/глобальні типи
│   ├── i18n/                   # конфіг + переклади react-i18next
│   └── constants/
├── tsconfig.json
├── tsconfig.app.json
├── tsconfig.node.json
└── vite.config.ts
```

Правила:
- **`components/` (корінь `src/`)** — тільки спільні, "дурні" UI-елементи
  без бізнес-логіки та без знання про конкретну фічу (кнопки, модалки,
  інпути, лейаути). Кожен такий компонент — власна папка з `.tsx` +
  `.css`, як і раніше.
- **`features/<name>/`** — вся логіка, специфічна для домену
  (наприклад: `projects`, `documents`, `reports`, `norms`, `inbox`,
  `auth`). Усередині фічі:
  - `components/` — компоненти, що мають сенс лише в межах цієї фічі;
    вони НЕ отримують окремий `.css` на кожен компонент — стилі йдуть в
    один спільний `<feature>.css` фічі (плюс Bootstrap-утиліти там, де
    цього достатньо). Не плодити `.css` на кожен файл усередині фічі.
  - `services/` — виклики API та бізнес-правила саме цієї фічі (аналог
    backend-сервісу, але на фронтенді).
  - `hooks/`, `types/` — локальні для фічі.
  - `index.ts` — єдина точка експорту назовні (barrel file). Інші фічі
    та `pages/` імпортують тільки з `features/<name>` (через `index.ts`),
    ніколи не лізуть у внутрішні файли іншої фічі напряму
    (`features/projects/components/...` з іншої фічі — заборонено).
- **`pages/`** — тільки route entry points: збирають фічі докупи,
  підвантажують дані верхнього рівня, не містять власної бізнес-логіки.
- **`routes/`** — уся конфігурація маршрутів на **React Router**, не
  розкидана по `App.tsx`/сторінках.
- **`store/`** — глобальний клієнтський стан на **Zustand**. Серверний
  стан (дані з API) — через `features/*/services`, не дублювати
  серверні дані в Zustand-store вручну. Додавання бібліотеки
  серверного стану (React Query тощо) — окреме рішення команди, не
  побічний ефект однієї фічі (розділ 3).
- **`services/` (корінь `src/`)** — тільки глобальна конфігурація API
  (базовий axios/fetch-інстанс, interceptors, обробка помилок/токенів).
  Доменні виклики API живуть у `features/<name>/services`, не тут.
- Стилі — Bootstrap для базової сітки/утиліт + CSS на рівні
  компонента (спільні) або на рівні фічі (усередині `features/`). Не
  додавати Tailwind, не змішувати два фреймворки стилів в одному
  проєкті.
- Локалізація — тільки через `react-i18next` (`i18n/`), українська та
  англійська як мінімум. Ніяких хардкод-рядків інтерфейсу в JSX.
- Стан теми (світла/темна) і мова — через `providers/`, не через
  локальні useState в кожному компоненті окремо.

### 2.2 Backend — обов'язкова структура

```text
backend/
├── app/
│   ├── core/            # конфіг, підключення до БД, DI, налаштування застосунку
│   ├── database/
│   │   ├── models.py    # Tortoise-ORM моделі
│   │   └── migrations/  # нумеровані SQL-міграції (розділ 3), Aerich не використовується
│   ├── schemas/         # Pydantic-схеми запитів/відповідей (контракт API)
│   ├── routers/
│   │   └── <domain>/
│   │       └── view.py  # тільки HTTP-шар: валідація запиту, виклик сервісу, серіалізація відповіді
│   ├── services/         # бізнес-логіка домену (router -> service -> repository)
│   ├── repositories/     # доступ до даних через Tortoise ORM (router і service НЕ звертаються до моделей напряму для складних запитів)
│   ├── ai/                # абстракція над AI-провайдером (7.4) — інтерфейс + конкретна реалізація (напр. openrouter.py)
│   ├── rules/             # детермінована бізнес-логіка вердикту (порівняння матеріалів) — БЕЗ звернень до AI-шару
│   ├── prompts/           # версіоновані промпти (не рядки в коді) — детальніше розділ 8
│   ├── workers/           # ARQ-таски (фонова обробка листів/документів)
│   └── utils/
│       ├── classes/
│       ├── exceptions/
│       └── middlewares/
├── tests/
│   ├── unit/
│   ├── integration/
│   ├── golden/          # golden-набір кейсів для LLM-конвеєра (розділ 8)
│   └── conftest.py
├── main.py
├── pyproject.toml
├── uv.lock
└── requirements.txt      # згенерований з uv для Docker-образу, вручну не редагувати
```

Шарова архітектура є обов'язковою, не опціональною для MVP:

```text
router (view.py) → service → repository → Tortoise model
```

- `router`/`view.py`: тільки HTTP — приймає запит, валідує Pydantic-схемою,
  викликає один метод сервісу, повертає відповідь. Жодної бізнес-логіки.
- `service`: бізнес-правила домену (наприклад, "як порівняти матеріали",
  "як сформувати звіт"). Не знає про HTTP, не знає деталей SQL.
- `repository`: єдине місце, де є звернення до Tortoise-моделей для
  доменної логіки (прості одноразові вибірки в межах одного ендпоінту —
  допустимі напряму, але будь-яка логіка, що повторюється, виноситься в
  repository).
- Кожен тип фонового завдання (обробка листа, обробка документа,
  обробка нормативного файлу) — окремий модуль у `workers/`, а не один
  спільний "великий" воркер.
- `rules/` фізично відокремлений від `ai/`: сервіс, що обчислює вердикт
  (погодити/відхилити/потребує уточнення), не імпортує й не викликає
  нічого з `app/ai/`. LLM отримує вже готовий вердикт як факт для
  формулювання тексту, а не бере участь у його визначенні (див.
  розділ 8).

## 3. Технологічний стек (фіксований, не змінювати без явного запиту)

**Backend:**
- Python, FastAPI, повністю асинхронний код: `async def` всюди в
  routers/services/repositories, асинхронний драйвер `asyncpg`.
- Tortoise-ORM **версії 1.1.7**. Менеджер залежностей — **uv**
  (`pyproject.toml` + `uv.lock` — джерело істини; `requirements.txt`
  генерується з uv, наприклад `uv export`, для Docker-образу).
- PostgreSQL — основна БД.
- Redis + ARQ — черга фонових завдань.
- SMTP — власний поштовий сервер, розгорнутий через Docker
  Compose/Swarm, окрема адреса на кожен проєкт.

**Frontend:**
- React + TypeScript, Vite.
- Bootstrap для базових стилів/сітки. CSS — один файл на спільний
  компонент (`components/`) і один файл на фічу (`features/<name>/`),
  а не на кожен файл усередині фічі (точні правила — розділ 2.1).
- **React Router** — маршрутизація (`routes/`), **Zustand** — глобальний
  клієнтський стан (`store/`).
- `react-i18next` для багатомовності (укр/англ мінімум).
- Серверний стан — через `features/*/services`. React Query до стека не
  входить: додавати лише за окремим явним рішенням команди, не «по
  дорозі» в межах фічі.

**Джерело істини за версіями — лок-файли** (`backend/uv.lock`,
`frontend/package-lock.json`), а не перелік у цьому документі: будь-яка
таблиця версій у правилах застаріває через тиждень і починає
суперечити лок-файлу. Тут фіксуються тільки ті піни, що є частиною
архітектурного рішення (Tortoise-ORM 1.1.7 вище), решта живе в
лок-файлах. Додаючи нову залежність, звіряй її з реєстром за розділом
9 («реальність залежностей»): пакет існує, підтримується, назва не
є слопсквотом.

**⚠️ КРИТИЧНО: Aerich НІКОЛИ не використовується.**
Схема БД керується внутрішніми міграціями Tortoise-ORM (`Tortoise.generate_schemas`
для розробки, і явні SQL/скриптові міграції для продакшн-змін схеми — не
Aerich). Якщо потрібна зміна схеми в продакшні — писати міграційний скрипт
вручну в `app/database/migrations/`, ніколи не пропонувати встановити Aerich.

Дисципліна навіть без Aerich: одна гілка/задача — один міграційний
скрипт; скрипти нумеруються послідовно (`0007_add_material_specs.sql`
чи аналог) і застосовуються рівно в одному порядку. Якщо дві гілки
одночасно додають міграцію — та, що мержиться другою, перенумеровує
свій скрипт під актуальний "останній" перед мержем, щоб не було двох
скриптів з однаковим порядковим номером.

Оскільки Aerich не веде облік застосованих міграцій, цей облік
обов'язковий власноруч, інакше «яка версія схеми зараз на сервері»
стає здогадкою:
- окрема таблиця `schema_migrations` (номер скрипта, час застосування,
  контрольна сума файлу) — заповнюється раннером міграцій;
- ідентифікатор міграції — **унікальний ключ** таблиці, а не просто
  колонка: подвійне застосування того самого скрипта має падати на
  рівні БД, а не залежати від того, чи раннер правильно порівняв
  списки;
- раннер бере **блокування** на час роботи (advisory lock PostgreSQL
  або аналог) і виконується строго в одному екземплярі: під час
  паралельного деплою двох інстансів другий чекає, а не застосовує
  ті самі скрипти вдруге;
- зміна схеми й запис у `schema_migrations` відбуваються **в одній
  транзакції**: або застосувалося й зафіксувалося, або не сталося
  нічого. Інакше падіння між DDL і записом у журнал лишає схему
  зміненою, а журнал — ні, і наступний запуск застосує скрипт удруге;
- операції, які PostgreSQL не вміє відкочувати в транзакції
  (наприклад `CREATE INDEX CONCURRENTLY`), виносяться в окремий
  скрипт, позначений як нетранзакційний, і пишуться ідемпотентно
  (`IF NOT EXISTS`) — щоб повторний запуск після збою не ламав БД;
- раннер застосовує тільки ті скрипти, яких немає в таблиці, у
  порядку номерів, і падає, якщо контрольна сума вже застосованого
  скрипта змінилася (тобто хтось відредагував історію);
- вже змержений міграційний скрипт **ніколи не редагується** — правка
  оформлюється новим скриптом;
- `Tortoise.generate_schemas` допустимий тільки для локальної розробки
  й тестової БД, ніколи для staging/production.

## 4. Git-flow

Гілки:
- `main` — захищена, тільки продакшн-готовий код. **Ніколи не пушити в
  `main` напряму**, навіть для дрібних правок.
- `develop` — інтеграційна гілка.
- `feature/<short-description>` (або `fix/...`, `chore/...`) —
  створюється під кожну задачу/фічу від `develop`.

Процес:
1. Гілка `feature/...` створюється від актуального `develop`.
2. Робота ведеться в цій гілці.
3. Зміни йдуть у `develop` **тільки через Pull Request**, не прямим пушем.
4. `develop` → `main` — окремий процес релізу (не в межах звичайної
   фічі), теж через PR.

Якщо Claude працює над задачею і немає явної фіча-гілки — створити її
першим кроком, не комітити напряму в `develop`/`main`.

Ревʼю та мерж:
- PR мержиться за наявності **щонайменше одного апруву** й **зеленого
  CI**. Апрув без перегляду диффу — не апрув.
- **Фінальний мерж виконує техлід (Lilia) або Влад.** Решта команди
  робить ревʼю та апрув, але кнопку Merge не тиснуть — навіть на
  власному PR і навіть коли апрув уже стоїть.
- Один PR = одна задача з Trello. У описі PR — посилання на картку;
  беручи задачу, виконавець позначає себе учасником картки й переносить
  її в колонку «В роботі», щоб дошка відповідала стану гілок.
- Гілка створюється під кожну задачу окремо. Продовжувати роботу в уже
  відкритій гілці можна лише в межах тієї самої задачі.

**Виняток на час бутстрапу.** Правила вище описують сталий процес, але
самі приїхали в репозиторій раніше, ніж зʼявилася гілка `develop`.
Тому гілка `global-rules-init` мержиться напряму в `main` — це
одноразовий виняток для PR, що заводить самі правила. Він діє доти,
доки не створено `develop`; після цього всі фіча-гілки беруться від
`develop`, а `develop → main` лишається релізним процесом. Інші
«тимчасові винятки» так не оформлюються: якщо правило заважає — його
змінюють через PR, а не обходять мовчки.

Додаткові правила гігієни:
- **Код потрапляє в репозиторій файлами, ніколи архівом.** Не комітити
  `.zip`/`.tar.gz`/`.rar` з проєктом чи його частиною — навіть "щоб
  швидше передати фронт". Архів не має диффу: його неможливо
  відревʼювати, неможливо змержити, і він назавжди лишається в історії
  git. Якщо роботу віддали архівом у месенджері — розпаковує її той,
  хто відкриває PR, і комітить уже нормальною структурою (розділ 2).
  Те саме стосується будь-яких бінарників і зібраних артефактів
  (`dist/`, `build/`, `node_modules/`) — вони в `.gitignore`,
  а не в комітах.
- **Розмір PR:** не відкривати PR більший за ~400 рядків диффу (без
  згенерованих файлів і лок-файлів). Великі задачі — розбивати на
  послідовні PR, а не заносити однією гілкою.
- **Час життя гілки:** прагнути вливати `feature/...` в `develop`
  протягом дня-двох; тверда стеля — 2–3 робочі дні. Довгоживучі гілки
  роблять конфлікти злиття неминучими.
- **Коміти:** формат Conventional Commits — `type(scope): опис` (`feat`,
  `fix`, `docs`, `refactor`, `test`, `chore`).
- **CODEOWNERS:** якщо файл є — це підказка рецензенту "хто краще знає
  модуль", не обов'язковий блокуючий апрув власника (щоб не створювати
  вузьке місце на невеликій команді).

### 4.1 Що ганяє CI на кожен PR

Інші розділи посилаються на "крок CI" — ось повний перелік, щоб
посилання не були абстрактними. Усі кроки обов'язкові й зупиняють
мерж. Команди наведені **від кореня репозиторію**: у монорепо CI
стартує саме там, тому шляхи йдуть із префіксом `backend/` чи
`frontend/`. Кроки, для яких відповідної теки ще не існує,
пропускаються доти, доки вона не зʼявиться, — але не видаляються
зі списку.

1. Лінт і формат:
   `ruff check backend` + `black --check backend`;
   `npm --prefix frontend run lint` + `npx --prefix frontend prettier
   --check "frontend/src/**/*.{ts,tsx,css}"`.
2. Типи:
   `mypy --config-file backend/pyproject.toml backend/app/rules
   backend/app/schemas` — секція `[tool.mypy]` з `strict = true`
   лежить у `backend/pyproject.toml`, прапорці в команді не
   дублюються;
   `npx --prefix frontend tsc --noEmit -p frontend/tsconfig.app.json`
   (саме `tsconfig.app.json`, бо кореневий `tsconfig.json` лише
   посилається на проєкти через `references` — див. розділ 6).
3. Тести: `pytest backend/tests`.
4. Окремою командою — гейт покриття ядра вердикту:
   `pytest backend/tests/unit/rules --cov=backend/app/rules
   --cov-branch --cov-fail-under=100` (розділ 5).
5. `gitleaks detect --source . --redact` як окремий обов'язковий крок
   (розділ 10).
6. Перевірка, що згенеровані з OpenAPI TS-типи не розійшлися зі
   схемою: регенерація + `git status --porcelain
   frontend/src/api/schema.d.ts` має бути порожнім (розділ 6). Схема
   для генерації береться з дампу `app.openapi()`, без підняття
   сервера в CI.

Ті самі перевірки стоять у `.pre-commit-config.yaml` (файл комітиться в
репозиторій, кожен розробник робить `pre-commit install`). Pre-commit
дає швидкий фідбек, але його можна обійти через `--no-verify` — тому
дублювання в CI обов'язкове, а не надлишкове.

## 5. Тести

- Backend і воркери: **pytest**. Кожен новий ендпоінт/сервіс/repository-
  метод і кожен новий ARQ-таск повинні супроводжуватись тестами в
  `tests/unit/` (ізольована логіка, моки зовнішніх сервісів/БД) та за
  потреби `tests/integration/` (реальна тестова БД).
- Кожен API-ендпоінт FastAPI отримує щонайменше два інтеграційні тести:
  happy path і головний помилковий сценарій. Це мінімум для MVP, не
  повне комбінаторне покриття. Оскільки стек повністю асинхронний
  (розділ 3), тести ходять через `httpx.AsyncClient` +
  `ASGITransport` під `pytest-asyncio`, а не через синхронний
  `TestClient`: синхронний клієнт піднімає власний event loop і
  розходиться з loop, у якому ініціалізований Tortoise, що дає
  «плаваючі» падіння тестів.
- Ініціалізація тестової БД (Tortoise) і її очищення між тестами
  живуть у `tests/conftest.py` як фікстури, а не повторюються в
  кожному тестовому модулі.
- **Детермінований шар вердикту (`app/rules/`) покривається юніт-тестами
  на 100% гілок.** Це ядро продукту, яке підрядник може оспорити — тут
  економія часу на тестах неприйнятна. Гейт покриття (`--cov-fail-under=100`)
  живе в окремій CI-команді, а не в дефолтних `addopts` pytest (інакше
  локальний запуск pytest по одному файлу завжди падатиме).
- **Тести вердикту ніколи не мокають сам LLM** — вердикт має бути
  повністю тестованим без мережевого виклику до AI-провайдера, тому що
  його обчислює `app/rules/`, а не LLM (розділ 2.2, розділ 8). Якщо
  тест вердикту не проходить без API-ключа — це ознака, що рішення
  протекло в LLM-шар, а не факт, який треба замокати.
- AI-провайдер (`app/ai/`) у тестах завжди мокається — тести ніколи не
  роблять реальні виклики до зовнішнього AI-сервісу.
- Приховування чутливих даних (розділ 1) — окрема функція з власними
  юніт-тестами. Тести йдуть по всьому переліку з розділу 1 на
  представницьких зразках: імена й організації, email, телефони,
  адреси/локації, суми й номери договорів, ідентифікатори
  проєкту/документа, підпис у кінці листа. Перевіряється не лише те,
  що payload «виглядає чистим», а що конкретне значення дійсно
  відсутнє в тому, що йде до AI-провайдера.
- Окремий зразок — **суцільний вільний текст листа** (не структуровані
  поля), у який імена, контакти й суми вплетені в речення: саме там
  санітайзер ламається найчастіше, бо нема поля, яке можна «взяти й
  замінити». Тест перевіряє відсутність кожного оригінального значення
  в payload, а не загальну «чистоту» вигляду.
- Окремий тест на fail-closed поведінку: якщо на вхід приходить поле
  невідомого типу або таке, що не піддалося знеособленню, — payload
  відхиляється цілком, і тест стверджує **нуль викликів** до
  AI-провайдера (мок не отримав жодного звернення). Тест має падати,
  якщо хтось зробить санітайзер «пропускаючим за замовчуванням» або
  таким, що просто викидає проблемне поле.
- Не будувати повну e2e-піраміду під MVP: максимум 1–2 наскрізні
  сценарії (напр. завантаження листа → вердикт → звіт). e2e повільні й
  крихкі — решту покриваємо юніт- та інтеграційними тестами.
- Frontend: тести не є пріоритетом MVP, але якщо пишуться — без
  окремого запиту не додавати новий test-runner понад той, що вже є в
  проєкті.

## 6. Форматування та лінтинг (жорстко, без винятків)

**Python (backend):**
- Форматер: `black`. Лінтер: `ruff`.
- Оскільки форматер один — `ruff format` у проєкті не вмикається (два
  форматери переформатовували б файли один за одним), а `line-length`
  у конфізі `ruff` виставляється рівним налаштуванню `black` (88), щоб
  лінтер не сварився на рядки, які сам `black` і зробив.
- **mypy у strict-режимі обов'язковий для `app/rules/` і `app/schemas`
  (доменне ядро й контракти відповіді)** — типи ловлять "галюциновані"
  атрибути та розбіжності з рантаймом, найчастіший клас дефектів у
  AI-згенерованому коді.
- Перед тим як вважати backend-задачу завершеною — код має проходити
  `black --check`, `ruff check` і `mypy` без помилок. Не залишати
  відформатований вручну код, що відрізняється від виводу `black`.

**TypeScript/React (frontend):**
- Форматер: `prettier`.
- Лінтер: `eslint` (конфіг проєкту).
- `tsconfig` тримати в `strict: true` **плюс `noUncheckedIndexedAccess`**
  (сам по собі `strict` не додає `| undefined` на індексний доступ до
  масиву/об'єкта — саме ця опція ловить "порожній масив → undefined →
  крах у проді"). У Vite-конфігурації зі split-файлами ці опції мають
  стояти в `tsconfig.app.json` і `tsconfig.node.json`, а не тільки в
  кореневому `tsconfig.json` (кореневий лише посилається на них через
  `references` і сам код не типізує).
- `any` заборонений у новому коді — використовувати `unknown` і звужувати
  тип; лінтер-правило `@typescript-eslint/no-explicit-any` вмикається як
  помилка, не warning.
- Той самий принцип: код повинен проходити `eslint` і бути
  відформатованим `prettier` перед тим, як вважатись готовим.
- TypeScript-типи для API-контракту генеруються автоматично з OpenAPI-
  схеми FastAPI (напр. `openapi-typescript`), а не описуються руками.
  Контракт, який підтримується вручну, тихо розходиться зі схемою, коли
  хтось змінює ендпоінт і забуває оновити типи.

Не пропонувати альтернативні інструменти (наприклад `autopep8`,
`isort` окремо від `ruff`, `standard` замість `eslint`) без явного
запиту користувача.

## 7. Загальні принципи коду

- Універсальність за типом матеріалу (розділ 2.2 ТЗ): загальний конвеєр
  обробки — один для всіх матеріалів; індивідуальний тільки перелік
  характеристик, що витягується з нормативного документа. Не хардкодити
  назви/поля конкретного пілотного матеріалу в загальній логіці
  конвеєра — вони мають надходити з даних (нормативного документа), а не
  з коду.
- Кожен висновок системи зберігається як рекомендація, ніколи як
  автоматично застосоване рішення. Дія інженера з підтвердження/
  відхилення завжди явно фіксується в журналі дій (хто, коли, яке
  рішення) — це окрема сутність у БД, не побічний ефект іншого запису.
- Звіти версіонуються: правка звіту створює нову версію, попередні
  версії не перезаписуються і не видаляються.
- Фонова обробка (листи, документи, нормативна база) ніколи не блокує
  запит користувача в інтерфейсі — завжди через ARQ-таск, результат
  повертається користувачу окремо (polling/websocket/статус), а не в
  тілі синхронної HTTP-відповіді.

## 8. LLM-конвеєр

Вивід LLM-частини системи має бути відтворюваним і захищеним перед
підрядником — це вимога вища за зручність розробки, не опційна
оптимізація.

- **LLM ніколи не ухвалює вердикт.** Рішення "погодити / відхилити /
  потребує уточнення" завжди обчислює детермінований код `app/rules/`
  (розділ 2.2); LLM отримує готовий вердикт як факт і лише формулює
  його текстом для звіту. Промпт передає вердикт як вхідні дані, а не
  запитує його.
- **Кожне твердження у звіті — з посиланням на джерело** (документ +
  сторінка/розділ нормативного документа). Якщо джерела немає — поле
  позначається явним маркером "не знайдено в наданих матеріалах", а не
  заповнюється здогадкою LLM. Це правило коду з тестом (перевірка, що
  кожен факт має непорожній `source` або маркер відсутності), а не
  пункт PR-чеклиста.
- **Промпти — версіоновані файли** в `app/prompts/` (`.txt`/`.jinja`),
  не рядки, захардкожені в коді сервісу. Зміна промпту — окремий,
  явний коміт.
- **Виклик LLM — тільки з `temperature=0` і structured output/JSON
  schema.** Відповідь завжди валідується Pydantic-моделлю; при
  невалідній відповіді — retry, потім явний фейл (не "мовчазний"
  дефолт). Навіть `temperature=0` не гарантує повного детермінізму —
  тому валідація схемою обов'язкова, а не підстраховка.
- **Ретраї обмежені, а не "до перемоги".** Задаються в одному місці
  (`app/ai/`) і покривають: максимальну кількість спроб (орієнтир —
  2 повтори понад початкову), дедлайн на весь виклик разом із
  ретраями, експоненційну затримку з джитером між спробами і
  перелік помилок, які взагалі підлягають повтору (таймаут, 429,
  5xx, невалідна схема). Помилки, що не зникнуть від повтору
  (401/403, невалідний запит), падають одразу. Без цих меж один
  "залиплий" лист здатен тримати воркер і палити бюджет годинами —
  це та сама причина, з якої в розділі 8 стоїть денний ліміт витрат.
- **Golden-набір тестових кейсів** (типові + межові + суперечливі)
  лежить у `backend/tests/golden/` під git і ганяється на кожній зміні
  промпту чи моделі — ловить регресії, коли вивід "поплив" навіть без
  зміни коду (напр. провайдер оновив модель за тим самим
  ідентифікатором). Орієнтир розміру для MVP — 10–30 кейсів: еталонні
  висновки дають досвідчені інженери, і це найдорожчий ресурс проєкту,
  тож набір росте разом із тестуванням, а не набивається кількістю.
- **Golden-прогін у CI — офлайн і детермінований.** Реальних викликів
  до AI-провайдера в ньому немає (розділ 5): відповіді беруться із
  записаних фікстур поруч із кейсами або з детермінованого мока.
  Інакше тест починає падати від чужого релізу моделі й мережі, і
  команда швидко вчиться його ігнорувати. Порівняння: детермінована
  частина (вердикт, посилання на джерела, наявність дисклеймера) —
  точна звірка, розбіжність = провал; текст формулювання —
  скорери з порогом, зафіксованим у коді тесту разом із причиною,
  чому обрано саме це число.
- Живий прогін по справжньому провайдеру — окрема ручна процедура
  перед зміною моделі, а не крок CI. Її результат оновлює фікстури,
  і оновлення фікстур іде окремим комітом, щоб у діффі було видно,
  що саме змінилося у виводі моделі.
- **Кожен виклик LLM логується:** версія промпту, модель, кількість
  вхідних/вихідних токенів, вартість, latency — без сирого
  конфіденційного тексту проєкту в лозі (розділ 1, розділ 10).
  Вердикт у лозі — це **вхідне** поле `rules_verdict`, обчислене
  `app/rules/` і передане в промпт як факт; поле, що описує вивід
  моделі, називається окремо (напр. `llm_narrative_ref` — посилання
  на збережене формулювання, не сам текст). Двох різних сутностей під
  одним іменем "вердикт" у лозі бути не повинно: інакше з логів
  неможливо довести, що рішення ухвалив детермінований код, а не
  модель — а саме це доведення знадобиться, якщо підрядник оспорить
  висновок. Це дає видимість, яка фіча палить бюджет, і дані для
  розділу 9 (спостережуваність AI-викликів).
- **Юридичні вимоги — теж код, не тільки текст у ТЗ:**
  - кожен згенерований звіт містить блок дисклеймера (рішення ухвалює
    інженер, система лише рекомендує);
  - підтвердження/відхилення інженером журналюється дослівно (хто,
    коли, яке саме формулювання) — окрема сутність у БД (розділ 7);
  - **лист підряднику ніколи не відправляється системою автоматично**
    — після обробки лист завжди залишається у стані "чернетка", і
    відправка вимагає явної дії інженера. Не повинно існувати кодового
    шляху, що переводить лист зі стану "чернетка" в "надіслано" без
    людини.
- Опційно (після MVP, якщо бюджет стає відчутним): денний ліміт на
  витрати LLM API з алертами на 50/80/100% і на аномальну кількість
  токенів за один запит.

## 9. Перевірка AI-згенерованого коду

Ці правила застосовуються, коли Claude (чи будь-який інший AI-агент)
пише код у цьому репозиторії — до того, як задача вважається
завершеною:

- Перевіряти AI-згенерований код у фіксованому порядку: (1) лінтер,
  (2) типи (mypy/tsc), (3) існуючі тести, (4) відповідність вимогам
  задачі, (5) реальність залежностей. Значну частину дефектів AI-коду
  ловлять лінтер+типи+тести за перші хвилини, але не всі — далі
  перевіряється логіка й відповідність специфікації вручну.
- **Перевіряти кожну нову залежність, яку пропонує AI:** пакет реально
  існує, підтримується, назва не є "галюцинованою" чи схожою на
  типозаплутування (slopsquatting) справжнього пакету. Не додавати
  залежність "бо AI так написав" без цієї перевірки.
- Не приймати AI-код великими блоками копіпасту — дублікати логіки
  виносити в спільну функцію/модуль одразу, а не залишати "на потім".

## 10. Безпека та управління секретами

- **Секрети (DB credentials, OpenRouter API key, SMTP password, JWT
  secret тощо) — тільки через змінні середовища**, ніколи не хардкодити
  в коді, конфігах чи комітах. `.env` (і будь-які `.env.*`, крім
  `.env.example`) обов'язково в `.gitignore`; `.env.example` з
  плейсхолдерами замість реальних значень — комітиться як довідка.
- **`.gitignore` покриває й реальні проєктні дані**, не тільки секрети:
  документи/датасети проєктів (`*.pdf`, `*.xlsx`, `*.dwg`, теки `data/`,
  `datasets/`, `uploads/`) ніколи не потрапляють у репозиторій —
  випадковий коміт такого файлу є витоком конфіденційних даних
  замовника. Туди ж — архіви (`*.zip`, `*.tar.gz`, `*.rar`) і зібрані
  артефакти (`node_modules/`, `dist/`, `build/`, `.venv/`): архів
  особливо небезпечний тим, що приховує власний вміст — усередині
  цілком може виявитися `.env` із ключами, і жоден секрет-сканер його
  там не побачить.
- **Секрет-сканування — і локально, і в CI:** інструмент типу gitleaks
  вмикається і в pre-commit, і як окремий обов'язковий крок CI. Хук
  pre-commit можна обійти (`--no-verify`), CI-крок — ні, тому обидва
  шари потрібні одночасно.
- Читання конфігурації в backend — тільки через `app/core/` (Pydantic
  `BaseSettings` або аналог), інші модулі не читають `os.environ`
  напряму.
- **Автентифікація:** JWT (access + refresh token). Access token —
  короткий термін дії (напр. 15–30 хв), refresh token — довший, з
  можливістю revoke/ротації. Токени передаються так, щоб мінімізувати
  ризик XSS/CSRF (напр. httpOnly cookie для refresh, або явне
  обґрунтування іншого підходу).
- **Паролі:** хешування виключно через `argon2` або `bcrypt`, ніколи не
  зберігати у відкритому вигляді чи оборотному шифруванні.
  **`passlib` не використовуємо:** останній реліз — 1.7.4 від
  08.10.2020, бібліотека фактично не підтримується і ламається на
  сучасному `bcrypt` (≥4.1). Беремо `pwdlib` (обгортка над argon2/
  bcrypt із підтримкою) або `argon2-cffi` / `bcrypt` напряму.
  Хеш-алгоритм і його параметри задаються в одному місці
  (`app/core/`), а не розсипані по сервісах.
- **Авторизація:** навіть з одним типом користувача в MVP (головний
  інженер, "повний доступ") — доступ перевіряється явно на рівні
  router/dependency (FastAPI `Depends`), а не мається на увазі. Модель
  прав закладається так, щоб додавання нової ролі пізніше не вимагало
  переписування ендпоінтів.
- **CORS** налаштовується явним списком дозволених origin з конфігу
  (`app/core/`), ніколи `allow_origins=["*"]` разом із
  `allow_credentials=True` — така пара або не працює, або відкриває
  API стороннім сайтам.
- **Ендпоінти автентифікації** (login, refresh, скидання пароля) мають
  обмеження частоти спроб — інакше JWT-схема зводиться до перебору
  пароля. Лічильник **спільний для всіх воркерів і інстансів** (Redis,
  який у стеку вже є), а не в памʼяті процесу: за кількох uvicorn-
  воркерів локальний лічильник обходиться простим повтором запиту.
  Задокументувати в коді треба чотири речі: ключ ліміту (окремо за IP
  і за обліковим записом, щоб ні один IP не заблокував чужий акаунт,
  ні перебір з ботнета не пройшов повз), вікно й момент скидання,
  заголовки відповіді (`Retry-After` і `RateLimit-*`) і поведінку при
  недоступному Redis. Останнє — свідоме рішення, а не випадковість:
  для автентифікації вибираємо fail-closed (відмовити з 503), бо
  «Redis впав, пускаємо всіх» перетворює аварію на вікно для перебору.
- Приховування чутливих даних перед відправкою на зовнішній AI-сервіс
  (розділ 1) — це вимога безпеки так само, як і функціональна вимога;
  так само чутливі дані (паролі, токени, персональні/об'єктні дані)
  ніколи не виводяться у відкритому вигляді в логах чи error-контексті
  (розділ 11) чи в логах LLM-викликів (розділ 8) — маскувати завжди,
  включно з DEBUG-рівнем логування.
- У production секрети розгортання (БД, SMTP, AI API key) передаються
  через Docker secrets/секрет-менеджер оркестрації, не через звичайні
  `.env`-файли, скопійовані в образ чи репозиторій.

## 11. Спостережуваність та обробка помилок

- **Структуроване логування:** JSON-логи через `structlog` (або
  `logging` + JSON-formatter). Кожен запис включає correlation/request
  ID — проброшений через middleware для HTTP-запитів і прикріплений до
  контексту кожного ARQ-таску для фонової обробки, щоб один ланцюжок
  дій (лист → таск → AI-виклик → звіт) можна було простежити по логах
  наскрізно.
- **Обробка винятків:** кастомні класи винятків живуть в
  `app/utils/exceptions/` (структура вже закладена в розділі 2.2).
  Глобальні FastAPI exception handlers (`@app.exception_handler`)
  перетворюють їх на консистентний JSON error response (код помилки,
  повідомлення, request ID) — "сирі" 500 з traceback у відповіді
  користувачу неприпустимі.
- Кожен ARQ worker-таск обгортається try/except на верхньому рівні:
  помилка логується (traceback + контекст задачі) і не "проковтується"
  мовчки. Контекст задачі — це **непрозорі кореляційні ідентифікатори**
  (`correlation_id`, сурогатний `task_id`), а не внутрішні `projectId`/
  `documentId` у сирому вигляді: назва об'єкта чи номер документа самі
  собою є даними замовника (розділ 10), і в лог-агрегаторі їм не
  місце. Якщо для розбору інциденту потрібен саме внутрішній
  ідентифікатор — він або зберігається окремо з контрольованим
  доступом і зіставляється з `correlation_id` за потреби, або явно
  класифікується як нечутливий і маскується перед записом. Стан таски
  (успіх/провал) має бути видимим для інженера через API/UI, а не
  тільки в логах.
- **Health-ендпоінти:** `/health` (liveness) і `/ready` (readiness —
  перевірка з'єднання з PostgreSQL і Redis) обов'язкові з першої версії
  backend, потрібні для контейнерної оркестрації (Docker
  healthcheck/Swarm).
- **Моніторинг/error tracking:** інтеграція з Sentry (або аналогом) —
  підключати на ранньому етапі розробки, не відкладати "на потім".
  Латентність AI-викликів (`app/ai/`) і довжина/затримка ARQ-черги
  логуються/метрикуються окремо від звичайних логів помилок, щоб можна
  було відрізнити "AI повільний" від "AI впав". Це та сама метадана,
  що збирається на рівні окремого LLM-виклику в розділі 8.
- Чутливі дані (розділ 10) ніколи не потрапляють у traceback, error-
  контекст чи payload, що йде в Sentry/лог-агрегатор. Це стосується і
  ідентифікаторів проєкту/документа: у Sentry йде `correlation_id`,
  за яким подію можна зіставити з внутрішніми даними в системі, а не
  самі ідентифікатори чи назви об'єктів. Sentry — зовнішній сервіс,
  тому вимога до нього така сама, як до зовнішнього AI-провайдера
  (розділ 1).
